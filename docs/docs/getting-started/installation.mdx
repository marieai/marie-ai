# Installation

Marie-AI 5 uses Python 3.12 and uv-managed environments. The source checkout
keeps runtime dependencies in `pyproject.toml` and resolved Docker inputs in
`uv.lock`.

## Prerequisites

- Ubuntu 24.04 LTS
- Python 3.12
- uv
- Docker with BuildKit
- NVIDIA Container Toolkit for CUDA builds and runtime
- Local model zoo mounted at `/mnt/data/marie-ai/model_zoo`

## Install As A Project Dependency

Use uv in the application that depends on Marie-AI:

```shell
uv add marie-ai
```

For the CLI as a standalone tool:

```shell
uv tool install marie-ai
marie --help
```

## Develop From Source

Clone the repository, then install the profile you need.

```shell
git clone https://github.com/marieai/marie-ai.git
cd marie-ai
git checkout develop
```

CPU gateway profile:

```shell
uv sync --group dev
uv run marie --help
```

CUDA profile:

```shell
uv sync --locked --extra cu130 --group dev
uv run --locked --extra cu130 python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

Keep `--extra cu130` on CUDA `uv run` commands. A plain `uv run` does not select optional extras, so it does not enforce the CUDA/ML package pins. `--locked` also prevents the command from changing the committed dependency resolution.

## Clean Virtual Environments

Two uv interfaces exist, and they behave differently with this repository:

- **Project interface** (`uv sync`, `uv run`) reads `[tool.uv.sources]` from `pyproject.toml`, so the repo-local wheels under `wheels/`, the `packages/marie-*` path packages, and the `pytorch-cu130` index are wired up automatically. Use this by default.
- **pip interface** (`uv venv` + `uv pip install`, per the [uv docs](https://docs.astral.sh/uv/pip/environments/#using-a-virtual-environment)) does **not** apply `[tool.uv.sources]` — wheel locations and indexes must be passed explicitly. Use it when the environment must be fully under your control (side-by-side lanes, bisecting, CI shells).

If Python 3.12 is not present, let uv manage it:

```shell
uv python install 3.12
```

### Central Environment Layout

By default `uv sync` creates `.venv` inside the repository. We keep all environments in one place instead — `~/environments/` — and symlink `.venv` to the environment the checkout should use:

```shell
uv venv ~/environments/marie-ai-py312 --python 3.12
ln -sfn ~/environments/marie-ai-py312 .venv
```

uv, `uv run`, and IDE tooling resolve the `.venv` symlink normally, so from here the standard project flow works unchanged:

```shell
uv sync --locked --extra cu130 --group dev
uv run --locked --extra cu130 marie --help
```

To rebuild the environment from a clean slate, clear the target and re-sync — the symlink stays in place (`--clear` wipes the environment at that path):

```shell
uv venv ~/environments/marie-ai-py312 --python 3.12 --clear
uv sync --locked --extra cu130 --group dev
```

Note that `rm -rf .venv` only removes the symlink, not the environment. Switching a checkout to another lane is just re-pointing the link:

```shell
ln -sfn ~/environments/marie-ai-pytorch-2-12 .venv
```

`UV_PROJECT_ENVIRONMENT=~/environments/<name>` is an alternative per-shell override, but the symlink keeps the mapping visible and persistent.

### Repair a Stale Editable Install

Editable installs record absolute source paths in the environment. If the same central environment was last synced from another checkout or worktree, commands may fail with errors such as:

```text
ModuleNotFoundError: No module named 'marie.cli'
```

From the checkout you want to run, repair the editable package paths with the command for that environment:

```shell
# CPU
uv sync --locked --group dev --inexact

# CUDA 13.0
uv sync --locked --extra cu130 --group dev --inexact
```

`--inexact` preserves runtime or plugin packages that are installed in the environment but are not declared in `uv.lock`. Verify the repaired CLI through the project entry point:

```shell
# CPU
uv run --locked marie --help

# CUDA 13.0
uv run --locked --extra cu130 marie --help
```

Do not share one central environment between active checkouts or worktrees. Each editable install rewrites package paths and command shebangs for the checkout that ran `uv sync` most recently. Give each checkout its own environment path and `.venv` symlink.

### Standalone venv With The pip Interface

Create the environment under `~/environments/` and activate it:

```shell
uv venv ~/environments/marie-ai-py312 --python 3.12 --clear
source ~/environments/marie-ai-py312/bin/activate
```

With the environment activated, `uv pip` targets it automatically. Because the pip interface ignores `[tool.uv.sources]`, pass `--find-links wheels` for the repo-local wheels and install the local path packages in the same invocation.

CPU gateway profile:

```shell
uv pip install \
  -e . \
  -e packages/marie-kernel \
  -e packages/marie-wasm \
  -e packages/marie-mem0 \
  -e packages/marie-mcp \
  --group dev \
  --find-links wheels
```

CUDA profile (requires the native wheels under `wheels/`, see the next section):

```shell
# 1) torch/torchvision from the cu130 index
uv pip install torch==2.12.1 torchvision==0.27.1 \
  --index-url https://download.pytorch.org/whl/cu130

# 2) everything else, including the local native wheels
uv pip install \
  -e ".[cu130]" \
  -e packages/marie-kernel \
  -e packages/marie-wasm \
  -e packages/marie-mem0 \
  -e packages/marie-mcp \
  --group dev \
  --find-links wheels \
  --extra-index-url https://download.pytorch.org/whl/cu130 \
  --index-strategy unsafe-best-match

# 3) omegaconf Python 3.12 compatibility patch
python patches/patch-omegaconf-py312.py --no-confirm

# 4) confirm the resolution is consistent
uv pip check
```

`--index-strategy unsafe-best-match` mirrors the `[tool.uv]` setting the project interface uses; without it the cu130-index packages and PyPI packages cannot be mixed in one resolution.

Do not install `vllm`, `flash-attn`, `torchaudio`, or `faiss-gpu-cu12` into this environment; they are excluded from the torch 2.12/cu130 lane.

### Upgrading Individual Packages In A Lane Environment

Torch must be installed first and must never be replaced as a side effect. PyPI's default `torch` is not the cu130 build, so a plain `uv pip install -U <package>` that resolves a torch requirement will silently swap `torch 2.12.1+cu130` for a generic PyPI torch and break the CUDA stack (this has happened — a `sentence-transformers` upgrade did exactly this).

When upgrading or adding a single package in an existing lane environment, either skip its dependency resolution:

```shell
uv pip install --no-deps -U sentence-transformers
```

or re-pin torch in the same invocation so the resolver cannot move it:

```shell
uv pip install -U sentence-transformers \
  torch==2.12.1 torchvision==0.27.1 \
  --extra-index-url https://download.pytorch.org/whl/cu130 \
  --index-strategy unsafe-best-match
```

After any ad-hoc install, verify the stack is intact:

```shell
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

Expected: `2.12.1+cu130 True`. If torch was replaced, restore it with `uv pip install torch==2.12.1 torchvision==0.27.1 --index-url https://download.pytorch.org/whl/cu130`.

To also discard cached wheels and force fresh downloads on the next install:

```shell
uv cache clean
```

## Provision The wheels/ Artifacts

The CUDA profile expects the distributed wheels — `etcd3`, `fastwer`, Marie's fairseq fork, detectron2, and FAISS CUDA 13 — to exist under `wheels/`. They are published as a versioned GitHub release (`wheels-torch212-cu130`) rather than tracked in git, with the generated inventory in `wheels/README.md` as the SHA256 source of truth.

Fetch and verify them:

```shell
scripts/fetch-wheels.sh          # download missing artifacts and check SHA256s
scripts/fetch-wheels.sh verify   # check what is already present
```

The script prefers the `gh` CLI (required for private releases); `curl` with `GITHUB_TOKEN` is the fallback.

### Rebuild From Source

You do not have to configure the native build toolchain by hand — `scripts/setup-py312-torch212-cu130.sh` automates the whole Python 3.12 / PyTorch 2.12 / CUDA 13 lane: venv creation, torch/torchvision from the cu130 index, the CUDA 13 `nvcc` toolkit and library symlinks, source checkouts at the pinned refs, patches, and the wheel builds themselves.

For a brand-new environment, one command runs everything end to end, including the native/GPU verification gates:

```shell
MARIE_TORCH_ENV_NAME=marie-ai-pytorch-2-12 \
  scripts/setup-py312-torch212-cu130.sh all
```

If you already have a build environment, prep it once and then build every wheel with a single step — no guessing at the order:

```shell
export MARIE_VENV_BASE=~/environments
export MARIE_TORCH_ENV_NAME=marie-ai-pytorch-2-12

# one-time environment prep
scripts/setup-py312-torch212-cu130.sh venv       # Python 3.12 venv + build tools, symlinks .venv to it
scripts/setup-py312-torch212-cu130.sh torch      # torch 2.12.1 / torchvision 0.27.1 (cu130)
scripts/setup-py312-torch212-cu130.sh app-deps   # Marie editable install + test/runtime helpers

# builds cuda-toolkit, fastwer, fairseq, detectron2, and FAISS in order,
# then validates wheels/ and refreshes the README inventory
scripts/setup-py312-torch212-cu130.sh build-wheels
```

`build-wheels` checks its prerequisites and tells you which step is missing instead of failing mid-build. Run `scripts/setup-py312-torch212-cu130.sh help` for the full step list. Every step writes full command output under `command-output/repro-*`, including the invocation script needed to reproduce the run.

Both paths finish with the `wheels/README.md` inventory already refreshed, so publishing the new artifacts for other checkouts is just:

```shell
scripts/fetch-wheels.sh publish
```

## Docker Images

Use the repository build script. It stages a small build context, selects the
current Python 3.12 Dockerfiles, and installs from the uv lock files.

```shell
./build.sh marie-gateway-cpu
./build.sh marie-cuda
./build.sh all
```

The active Dockerfiles are:

- `Dockerfiles/cpu-312.slim.Dockerfile`
- `Dockerfiles/cuda-312.Dockerfile`

## Verify Runtime

CPU smoke:

```shell
uv run python -c "import marie; print(marie.__version__)"
```

CUDA smoke:

```shell
uv run --locked --extra cu130 python - <<'PY'
import torch
import detectron2
import faiss
import transformers

print("torch", torch.__version__, torch.version.cuda)
print("cuda", torch.cuda.is_available())
print("detectron2", detectron2.__version__)
print("faiss_gpus", faiss.get_num_gpus())
print("transformers", transformers.__version__)
PY
```
